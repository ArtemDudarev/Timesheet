# Аудит несоответствий: фронтенд-макет TS(9) vs текущий бэкенд

## Контекст

В `TS (9)/` лежит статический React/Babel-прототип (design handoff), полностью на моках (`window.DB` из `data.js`, **нет ни одного `fetch`/`axios`-вызова**). Бэкенд — 4 живых микросервиса (`auth_service`, `management_service`, `profile_service`, `timesheet_service`; `manager_service` — мёртвый, заменён на `management_service`, в docker-compose не подключён). Задача: сопоставить, что рисует фронт, с тем, что реально отдаёт API, и выписать разрывы для дальнейшего планирования разработки.

Авторитетная версия фронта — **корневые файлы `TS (9)/*.jsx`** (грузятся через `Табель.html`), а не `design_handoff_tabel/prototype/` (устаревший, меньший снэпшот без Admin/Absences). Ниже разбор по корневой версии.

## 2 и 3. Потребности экранов vs покрытие бэком

### Auth (`screen-login.jsx`, `screen-settings.jsx`→Безопасность)
| Нужно фронту | Бэкенд |
|---|---|
| Логин email+password → токен+роль/права | ✅ `POST /auth/login` (auth_service), JWT содержит `roles`+`permissions` |
| Refresh / logout | ✅ `POST /auth/refresh`, `POST /auth/logout` |
| Смена пароля (self-service) | ✅ `POST /auth/password/change` |
| Список активных сессий + завершение | ✅ `GET /auth/sessions/`, `DELETE /auth/sessions/{id}`, `DELETE /auth/sessions/` — уже реализовано, фронт сейчас просто рисует моки вместо реального вызова |
| "Забыли пароль" | 🟡 **частично гэп, уточнено пользователем**. Сам сброс (`POST /auth/password/reset/{user_id}`) верно ограничен `user:reset_password` (Менеджер/Администратор) — это НЕ self-service reset, и правильно. Но по замыслу нажатие "забыл пароль" должно создавать **заявку**, которая попадает в очередь менеджера (в `data.js` это уже смоделировано: `PasswordReset{id, empId, status: pending/done, requestedAt, tempPwd}`, в `screen-manager.jsx` — пульсирующий бейдж "запрос временного пароля"). Такой сущности "заявка на сброс" в бэкенде **нет вообще** — ни модели, ни `POST /auth/password/reset-requests` (публичный, по email/номеру, без аутентификации — пользователь ведь не может войти), ни `GET .../reset-requests` (список для менеджера, `user:reset_password`), ни привязки к нотификациям. Нужно завести отдельную сущность запроса, отдельную от самого действия сброса |

### Профиль (`screen-profile.jsx`, `employee-card.jsx`)
| Нужно фронту | Бэкенд |
|---|---|
| Данные сотрудника (имя, грейд, отдел, email, телефон, адрес, ДР, аватар) | ✅ `GET /employees/{id}` (profile_service) |
| Список проектов сотрудника + роль | ✅ реплика assignments в profile_service |
| Навыки | ✅ `GET /skills`, скиллы внутри `GET /employees/{id}` |
| KPI: часы/норма/утилизация/остаток | 🟡 частично — `GET /employees/{id}/summary` (timesheet_service) даёт месячную сводку; нет отдельного "остаток до нормы" — вычислимо на фронте |
| Недельный спарклайн часов («Динамика часов», ровно 8 недель на скриншоте) | ❌ нет агрегации по неделям — нужен `GET .../weekly-hours?weeks=8`-подобный endpoint либо агрегация `GET /periods/{id}/entries` на клиенте (дороже при 8-недельном окне, может пересекать границы периодов/месяцев) |

### Табель (`screen-timesheet.jsx`)
| Нужно фронту | Бэкенд |
|---|---|
| CRUD записей времени по дню/проекту/задаче | ✅ `POST/PATCH/DELETE /periods/{id}/entries/{eid}` (timesheet_service) |
| Периоды (месяц) | ✅ `GET /periods/`, `GET /periods/{id}` |
| Производственный календарь (праздники/короткие дни) | ✅ `GET /production-calendar/{year}` |
| Overtime → отдельное согласование | ✅ `OvertimeApproval` создаётся автоматически, `GET/POST /overtime-approvals/...` |
| **Submit-for-approval на уровне периода** (draft→pending→approved/rejected) | ❌ **нет**. `TimesheetPeriod.status` знает только `OPEN`/`CLOSED`; закрытие — `POST /periods/{id}/close`, требует `timesheet:close_period` (админ/менеджер), это НЕ "сотрудник отправил табель на согласование" |

### Управление / Manager (`screen-manager.jsx`)
| Нужно фронту | Бэкенд |
|---|---|
| CRUD проектов | ✅ `POST/GET/PATCH/DELETE /projects` (management_service, `project:manage`) |

Нет `code/color/client/lead_id/budget/spent/deadline/progress/tasks*`. **Подтверждено скриншотом** «Управление → Проекты»: колонка РУКОВОДИТЕЛЬ (Дмитрий/Павел) — поля для проектного руководителя (не путать с `Employee.lead_id`, это оргструктура) в модели нет вообще |

| **Создание нового сотрудника через форму менеджера** | ✅ **by design, не гэп** — `POST /auth/register` уже защищён `user:register`, которым владеют только **Менеджер** и **Администратор** (проверено в `seed.py`), то есть создание сотрудника и так намеренно доступно только им, ровно как и задумано. Employee-профиль после этого создаётся автоматически по Kafka (`user.created`) с дефолтным статусом. Реальный (некритичный) момент — не отсутствие прав, а UX/оркестрация: одношаговый визард фронта ("имя+грейд+отдел+роль+скиллы+проект за один сабмит") бэкенду не соответствует — потребуется собрать его как последовательность вызовов (`POST /auth/register` → `PATCH /employees/{id}/lead`, `/status`, `/roles`, `PATCH /employees/{id}` в profile_service для грейда/отдела, `PUT /employees/{id}/skills`, `POST /employees/{id}/assignments`) с обработкой промежуточных ошибок. **Подтверждено скриншотом**: аналогичная кнопка «Новый пользователь» есть ещё и в Админ-панели → Пользователи — второй вход в тот же процесс, нужен единый переиспользуемый оркестратор, а не дублирование логики в двух местах |
| Выдача временного пароля | ✅ `POST /auth/password/reset/{user_id}` — уже есть, фронт сейчас генерирует пароль **на клиенте** (неправильно, нужно вызывать backend) |
| Согласование overtime | ✅ `/overtime-approvals` |
| Согласование командировок (trip absences) | ❌ нет — Absence-домена не существует |

## 4. Приоритизация: 3 группы

Критерий группировки — не "насколько это большая фича", а **что должно существовать, чтобы работал базовый цикл табелирования** (Login → Профиль → Табель: заполнил → отправил → менеджер согласовал → Управление/Отчётность по факту). Всё, без чего этот цикл физически не может замкнуться — критичный путь. Всё, что делает продукт полноценным, но не блокирует сам цикл — второстепенное. Отдельные крупные домены, которые сейчас не привязаны к денежному/операционному циклу табеля — можно оставить на моках.

### 🔴 Критичный путь — без этого фронт не заработает как MVP табелирования

Почти всё здесь **уже есть в бэкенде** — нужен только wiring (замена fetch на реальные вызовы вместо `window.DB`). Один пункт (#5) — реальный недостающий backend-функционал, без него цикл не замыкается.

1. **Auth wiring**: `POST /auth/login/refresh/logout` — заменить fake 650ms timeout, хранить JWT, гейтить роуты по `permissions` из токена
2. **Профиль wiring**: `GET/PATCH /employees/{id}` (profile_service), `PUT /employees/{id}/skills`
3. **Табель wiring**: `GET /periods/`, `POST/PATCH/DELETE /periods/{id}/entries`, `GET /production-calendar/{year}`
4. **Проекты/назначения wiring** (для экрана Управление): `CRUD /projects`, `POST/PATCH/DELETE /employees/{id}/assignments`, `GET /employees/`
5. **Period-level submit/approve workflow** ❌ — **единственный настоящий пробел в критичном пути**. Сейчас `TimesheetPeriod.status` = только `OPEN/CLOSED`, закрытие — админская операция, а не "сотрудник отправил → менеджер согласовал/отклонил". Без этого golden path (см. скриншот статуса «Черновик» + кнопка «Отправить на согласование») физически нельзя пройти до конца. Разрабатывать в первую очередь.
6. **Overtime approval wiring**: `/overtime-approvals` — уже есть, нужен только wiring (по факту это часть того же цикла, раз переработка попадает в согласование автоматически)

### 🟡 Второстепенное — делает продукт полноценным, но цикл табелирования и без этого замыкается

7. **Reporting service** (аналитика/KPI/план-факт) + серверный Excel-экспорт (`.xlsx`, не CSV)
8. **Обогащение модели `Project`**: code/color/client/lead_id(руководитель)/budget/spent/deadline/progress/tasksDone-Total — нужно для содержательного экрана Управление/Отчётность, но CRUD-каркас уже работает и без этих полей
9. **Notification service** — событийные (approval/doc/chat/deadline/mention/password) + периодические (еженедельный дайджест, cron)
10. **Заявка на сброс пароля** (`PasswordResetRequest` + публичный create + менеджерский list/resolve) — сам сброс уже работает, не хватает только очереди заявок
11. Недельная агрегация часов (`weekly-hours?weeks=8`), "последние записи" convenience-эндпоинт — иначе точечно собираются на клиенте
12. `TimeEntry.comment` → тред комментариев (сейчас одно строковое поле)
13. Admin API — объединить неймспейс (`/admin/*` в auth_service vs `/roles` в management_service) — функционально всё работает, это чисто вопрос API Gateway/консистентности
14. CSV/Excel-экспорт самого табеля (не только отчётов)

### 🟢 Можно оставить замоканным — отдельные домены, сейчас не горят

15. **Document service** (e-signature, маршруты подписания, загрузка файлов, шаблоны) — полностью отдельный эпик, у Табеля есть самостоятельная ценность и без документооборота
16. **Chat service + WebSocket** — отдельный эпик; встроенные в чат approval-карточки к тому же дублируют Manager→Согласование и не нужны, пока нет реального чата
17. **Absence/Leave service** (отпуска/больничные/командировки, баланс отпуска) — используется в 3 экранах, но сам цикл табелирования не блокирует: можно временно скрыть/заглушить оверлей отсутствий в Табеле и approve-tab для командировок в Manager, согласование переработок и так работает независимо через `OvertimeApproval`
18. **Кастомные permission-коды** (создание нового *права*, не роли) — не поддерживается по дизайну (см. [[project-casbin-rbac]]), оставить недоступным в UI, а не реализовывать
19. Глобальный поиск по проектам/сотрудникам в топбаре — сейчас декоративный, отдельный агрегирующий endpoint не нужен для MVP

### Как это использовать

Группы 🔴 задают порядок первого спринта (в основном wiring + один backend-таск #5). 🟡 — бэклог следующих 1-2 спринтов, приоритезируется по продуктовой ценности отдельно. 🟢 — не планировать, пока нет явного запроса на Documents/Chat/Absences как отдельные продуктовые эпики; на экранах фронта можно либо скрыть эти пункты меню, либо оставить как есть на моках без обещания рабочего API.

## 5. Критический взгляд на приоритизацию (self-review)

При повторной проверке нашёл, что часть пунктов 🔴 промаркирована как "просто wiring" необоснованно оптимистично, а один пункт вообще выпал из списка. Зафиксировано после **фактической** проверки кода (не предположений):

**1. CORS настроен только в auth_service — подтверждено grep'ом.** `management_service`, `profile_service`, `timesheet_service` **не имеют `CORSMiddleware` вообще** (проверено в их `src/main.py`, все три — `NO CORS FOUND`). Раз в `docker-compose.yml` нет ни nginx, ни api-gateway, ни reverse-proxy (grep пустой) — фронт должен ходить напрямую в 4 разных origin (порты 8001-8004). Браузер молча заблокирует запросы к 3 из 4 сервисов до тех пор, пока туда не добавят `CORSMiddleware` с правильным `allow_origins`. Это значит пункты 2-4 и 6 в 🔴 — **не "просто wiring", а требуют минимум одного backend-таска на сервис** (добавить CORS-мидлварь) прежде чем фронт вообще что-то получит в ответ.

**2. Создание сотрудника выпало из приоритизации.** В предыдущем сообщении оно было (п.15 старого списка "by design, не гэп"), но при перегруппировке на 🔴/🟡/🟢 я его никуда не вписал. По факту это нужно отнести в 🟡 (не блокирует цикл табелирования для уже существующих сотрудников, демо-аккаунтов достаточно для MVP-тестирования), но это реальный пробел в списке, а не решение — без него систему нельзя реально ввести в эксплуатацию за пределами seed-данных.

**3. Оркестрация создания сотрудника (register → 5 PATCH/PUT/POST) не имеет саги/отката.** Если 2-й или 3-й вызов из цепочки упадёт (сеть/сервис недоступен), получится наполовину созданный сотрудник (User есть, Employee создан Kafka'ой с дефолтным статусом, но грейд/отдел/lead/роли/скиллы не проставлены) без встроенного механизма докрутить или откатить. Раньше я описал это просто как "нужно собрать как последовательность вызовов" — этого недостаточно, нужен явный UI-статус "черновик сотрудника" с возможностью дозаполнить, а не транзакционная иллюзия.

**4. Уведомления — сомнительна отметка "🟡 второстепенное".** Колокольчик с бейджем непрочитанных виден в топбаре **на каждом экране**, а не только на отдельной странице (в отличие от, например, Reports). Если он останется полностью замокан, это не "неполный отдельный экран", а видимый на 100% времени сломанный/фейковый элемент интерфейса. Разумный компромисс — не полноценный Notification-service с cron-дайджестом (это ок оставить в 🟡), а на первом этапе хотя бы честно показывать пустое состояние ("уведомлений нет") вместо хардкод-моков — иначе продукт выглядит недоделанным на каждом экране, а не только там, где реально нет фичи.

**5. Kafka без outbox pattern — риск именно для нового критичного таска #5.** В BACKLOG уже отмечено (см. память [[project-overview]]), что publish идёт после commit без outbox/retry. Пункт 5 (period-level approve/reject) — это новая таблица + новые Kafka-события статуса периода. Если паттерн publish-after-commit сохранится и здесь, при сбое паблиша после коммита статус изменится в timesheet_service, но событие для менеджерской очереди/уведомлений может потеряться молча. Раз это первый по приоритету новый backend-таск, стоит либо сразу закладывать outbox, либо явно принять риск, а не переносить его молча.

**6. "Absence можно мокать" — не проверено, влияет ли отсутствие на норму часов.** Не выяснено, вычитает ли `TimesheetPeriod`/`summary` одобренный отпуск/больничный из нормы (151ч). Если Absence-домена нет и это не проверено, сотрудник в отпуске будет либо ошибочно должен закрыть полную норму часов, либо (если норма считается только по production calendar) это разойдётся с реальностью до тех пор, пока Absence не появится. Не блокирует MVP, но это осознанный, а не случайный, трейд-офф — стоит явно задокументировать, а не просто "скрыть оверлей".

**7. "Chat можно мокать" — недостаточно чётко: кнопки Approve/Reject в чате должны быть либо убраны, либо явно отключены, а не просто оставлены как есть.** Встроенные approval-карточки в чате выглядят как настоящие рабочие кнопки. Если Chat остаётся полностью замокан, а Timesheet/Manager approval — реальны, то нажатие "Согласовать" в чате не подтверждает переработку по-настоящему — это может ввести менеджера в заблуждение (решил, что согласовал, — а по факту нет). Для 🟢-статуса Chat нужно либо скрыть эти кнопки, либо явно пометить "демо", а не "оставить как в прототипе".

**Итог:** ядро приоритизации (🔴 = золотой путь табеля + один backend-гэп #5, 🟢 = Documents/Chat/Absences как отдельные эпики) не меняется, но: (a) CORS — скрытый предварительный таск перед любым wiring, (b) создание сотрудника нужно вернуть в список явно, (c) уведомления стоит хотя бы частично поднять в приоритете из-за глобальной видимости в UI, (d) два пункта (#5 нового списка, absence-mock) несут риски, которые раньше были подразумеваемыми, а не явными.
